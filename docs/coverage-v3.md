# 覆盖率口径 v3：为什么要把「英文句子」和「标识符」拆开

> 本文记录 `metricVersion: 3` 的设计依据、实测数据与已知局限。
> 样本来源：作者本机 76 个会话、25 条模型路由、约 1.1 万段 reasoning。
> 换一台机器、换一批模型，绝对数值会变，但结论方向可参考。

## 一、v2 的问题

v2 的口径是一个比值：

```
coverage = 汉字数 / 自然语言字符数
自然语言字符 = 全部字符 − 代码块 − 数字 − 标点 − 空白 − 符号
```

它想回答的问题是「这段思考是不是用中文写的」。但它把两类完全不同的东西
归进了同一个分母：

| 类别 | 例子 | 该不该算作「违规」 |
|---|---|---|
| 英文推理句子 | `Wait, I need to double-check whether it gets injected into every step.` | **应该** |
| 代码标识符 / 工具名 / 专名 | `ops_bash`、`Python`、`get_tree()`、`process_mode`、`sympy` | **不应该** |

而插件的注入文本本身明确允许后者保留原文：

> 即使题目、代码、路径或工具名是英文，也只允许在引用时保留原文；
> 代码、数学公式与专有名词保持原文。

于是出现了一个荒谬的结果：**模型完全遵循了指令，却因为遵循而被打低分。**

实测最能说明问题的一次：某会话的中文思考被判 `coverage = 0.3573`（远低于 0.6
阈值，会被标成失效），但同一段文本的构成是：

```
汉字        5320
英文句子     1164   ← 真正的违规量，占 7.8%
标识符      6556   ← 占 44%，全是代码与工具名
```

也就是说，44% 的「非中文」是豁免内容，却被算成不遵循。

## 二、v3 的做法

按「词」把非汉字部分一分为二，输出三个互斥量：

```
hanChars         汉字字符
englishChars     英文句子片段里的拉丁字符   ← 真正的违规量
identifierChars  标识符与专名字符           ← 豁免，不计违规

chineseRatio          = hanChars / (hanChars + englishChars)   ← 判定用这个
englishSentenceRatio  = englishChars / chars
identifierRatio       = identifierChars / chars
coverage              = cjk / chars（v2 原样保留，便于与旧日志对照）
```

`failed` 由 `chineseRatio < coverageThreshold` 判定。

### 片段切分

以汉字与代码符号为界切成「拉丁片段」。这里有个必须踩过才知道的坑：

如果按「词 + 任意非字母字符」贪婪切分，`sympy primepi(20000) 与 len(primerange(...))`
会被粘成一个片段并判成英文句子 —— 编码会话反而比 v2 更差。所以片段只允许被
**空白与英文行文标点**（`, ; : ! ? " ' ( ) [ ] { }`）连接；出现 `.` `/` `\` `=`
`->` 这类代码符号就断开。

### 片段判定

1. 片段内含英文虚词或高频动词（the / of / is / let / we / I …）→ 英文句子；
2. 否则片段有 ≥3 个连续普通英文词 → 英文句子（兜底，抓无虚词的短句）；
3. 否则 → 标识符（豁免）。

### 词级预分类（优先于词义）

含 `_ - . : / @ \ #` 或数字、驼峰形态（`opsBash`）、全大写形态（`ALWAYS`、`JSON`）
一律先算标识符。

这一条是实测逼出来的：`ALWAYS` 是 6 个字母，若不先判形态，它会命中副词
`always` 而被当成英文句子，导致一段标准中文思考被判 25% 覆盖率。

## 三、判定结论的变化

阈值 0.6。按 v2 → v3 的判定结果分三类：

### A. 被 v2 冤枉的（v2 failed → v3 通过）

| 路由 | v2 coverage | v3 chineseRatio |
|---|---:|---:|
| `workbuddy/cn:deepseek-v4.1-flash` | 56.6% | **95.5%** |
| `trae/deepseek-v4.1-flash` | 50.6% | **95.1%** |
| `trae/DeepSeek-V4-Flash` | 57.4% | **96.9%** |
| `raccoon/sn-deepseek-v4-1-flash-1017` | 55.8% | **91.9%** |
| `loomy/deepseek-v4-flash-1017` | 47.7% | **93.3%** |
| `codebuddy/global:hy4free` | 55.5% | **92.7%** |
| `workbuddy/cn:hy4free` | 52.9% | **82.3%** |
| `minimax/MiniMax-M3.1-Flash` | 52.4% | **71.8%** |

这些模型的标识符占比在 24%–35% 之间，v2 把豁免内容算成了违规。
**它们的能力没有变化，是 v2 的尺子不准。**

### B. 两口径都通过（结论不变）

`codearts/deepseek-v4.1-flash` 0.955、`lobsterai/deepseek-flash` 0.983、
`loomy/DeepSeek-V4.1-Flash` 0.992、`trae/Doubao-Seed-Code` 0.943、
`raccoon/sn-sensenova-6-8-flash` 0.969 等。

### C. 失效分级（段级均值口径，修正早期加权误判）

> **重要修正**：本节早期版本用的是**按字符加权**的 chineseRatio，它会被少数
> 超长英文段主导，把若干实际遵循的模型压成「失效」。下表改用**段级均值**
> （`tools/model-census.mjs` 的 segMean 列，110 会话 / 30 路由），并区分
> 「注入在场」与「从未注入」——后者不能算模型不遵循。

**真不遵循**（注入在场、样本充足、均值仍低）：

| 路由 | 段均 | 段数/会话 | 备注 |
|---|---:|---|---|
| `workbuddy/cn:kimi-k3.1-pro` | 3.6% | 145/10 | 全注入，稳定英文 |

**中等 / 临界**（注入在场，均值 0.4–0.7，是否拉黑须人工判断）：

| 路由 | 段均 | 加权(旧) | 段数/会话 |
|---|---:|---:|---|
| `qoder/qfmodel` | 42.0% | 10.9% | 61/3 |
| `loomy/spark-x2.6` | 55.8% | 23.7% | 202/3 |
| `aliyun/kimi-k3.1-pro` | 59.7% | 28.3% | 236/7 |
| `qodercn/qfmodel` | 71.4% | 42.7% | 1312/11 |

`qodercn/qfmodel` 段均 71.4% 但加权只有 42.7%、`loomy/spark-x2.6` 段均 55.8%
但加权 23.7% —— 加权口径把这两个实际中等偏好的模型误判成失效。作者实测
qfmodel「效果还不错」正是这个原因：加权值低，但多数会话是中文的。

**不能下结论**（从未注入，或注入样本过小）：

| 路由 | 段均 | 注入/未注入段 | 为何不算失效 |
|---|---:|---|---|
| `workbuddy/glm-5.3-flash` | 0.3% | 0/4 | 4 段全在插件安装之前 |
| `workbuddy/hy3` | 23.8% | 0/14 | 从未注入 |
| `workbuddy/step-5-preview` | 28.7% | 0/21 | 从未注入 |
| `acme-gateway/kimi-k3` | 6.5% | 6/65 | 仅 6 段注入，样本过小 |

**其实遵循良好**（注入段均高，加权被未注入历史段拉低）：

| 路由 | 注入段均 | 加权(旧) |
|---|---:|---:|
| `deepseek-account/deepseek-flash` | 97.6% | 42.4% |
| `acme-gateway/deepseek-flash` | 89.4% | 55.6% |

**结论修正**：真正稳定失效的只有 `workbuddy/cn:kimi-k3.1-pro` 一条。早期文档
列出的多条「失效」，大多是「加权口径 + 未注入历史样本」叠加造成的误判。

## 四、阈值标定

v3 的 `chineseRatio` 在真实数据上呈明显双峰：

```
遵循组   0.82 ─ 0.99
失效组   0.004 ─ 0.56
空档    0.56 ─ 0.82
```

默认阈值 `0.6` 正落在空档里，不需要调整。这也说明 v2 的 0.6 阈值本身没问题 ——
问题在分母，不在阈值。

## 五、已知局限

1. **不区分繁简**。口径按 `\p{Script=Han}` 统计，繁体字照样计入汉字。
   「要求简体」的判定目前做不到，需要一份繁简字形对照表（未实现）。
2. **行内代码处理不一致**。`chars`（v2 分母）不剔行内代码，v3 的分类会剔。
   这导致 `identifierRatio` 之和可能略小于 1，属预期。
3. **短片段易漏判**。单个不常见的英文词（不在虚词表里、也不构成三连词）
   会被算成标识符，使 `chineseRatio` 略偏高。方向是保守的（宁可放过）。
4. **绝对数值不可跨机器比较**。标识符密度取决于任务类型，编码会话天然
   标识符多。只应在同一台机器、同一批模型之间做相对比较。

## 六、对使用者的建议

- 看 **`chineseRatio`** 判断模型是否遵循；忽略 `coverage`（v2 遗留，仅用于对照旧日志）。
- 看 **`identifierRatio`** 理解差值来源：它高说明这段思考里代码多，不是模型偷懒。
- 看 **`englishSentenceRatio`** 判断违规程度：> 0.2 基本可以确认模型在写英文段落。
- 拉黑模型前，先看日志里的 `in/out` 分布（注入在场 / 不在场），
  避免把「注入之前的历史样本」误当成模型失效。
